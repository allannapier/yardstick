Install and your first run

There are two ways to drive yardstick: the ys command line, or the browser dashboard started with ys web up. This page takes the exact same first run through both -- start a proxy, start a run of arm-a, end it, look at the result -- using the repo's mocked smoke-test experiment, so either path costs exactly $0. Read Path A, Path B, or both; pick whichever fits how you like to work.

Shared setup

Both paths need the same three things first. You need Python 3.10 or newer and a clone of the yardstick repository; everything below is run from the repo root.

bash 
pip install -e .

This installs the ys CLI (a Typer app), litellm[proxy] to run the measurement proxy, fastapi/uvicorn for the dashboard, and pydantic for the experiment schema -- everything both paths below need.

yardstick keeps all of its own state -- the SQLite database of every proxied request, the active-run marker, the generated proxy config, pid/port files, and the dashboard's own experiment YAMLs -- under one directory, YARDSTICK_HOME. If you don't set that environment variable it defaults to ~/.yardstick. Both paths below assume the default.

Before starting either the CLI's proxy or the dashboard, you need a LITELLM_MASTER_KEY. This is not a key anyone issues you -- it's a shared secret you make up yourself, that authenticates your local harness to your local proxy. LiteLLM's proxy reads it as general_settings.master_key, and rejects any request that doesn't send it as a bearer token.

bash 
export LITELLM_MASTER_KEY=sk-ys-demo-1234

The exact same value has to be exported wherever you run ys proxy up and wherever you later run ys harness point (covered in tutorial 3) -- the harness sends this value back to the proxy as its API key, so a mismatch just looks like an auth failure. Pick one string and export it once per shell session.

Path A -- the CLI

Five commands: ys init, ys proxy up, ys start, ys end, ys proxy down. This path is entirely terminal-driven.

Initialise yardstick's home directory

ys init creates YARDSTICK_HOME (and an experiments/ subdirectory inside it) and initialises the database schema.

bash 
ys init
output 
yardstick home: /home/you/.yardstick
database initialised

"/home/you/.yardstick" will actually print as your own home directory. The database file itself lands at <YARDSTICK_HOME>/yardstick.db.

Start the proxy against the mock experiment

experiments/example.yaml is a smoke-test experiment shipped in the repo. Its single model, probe-claude-mock, is configured with litellm's mock_response field -- every request served under that model name gets back a canned string instead of ever reaching Anthropic. That's exactly what makes it safe to run end-to-end for free.

bash 
ys proxy up --exp experiments/example.yaml
output 
proxy ready at http://localhost:4000

Under the hood this reads every models: entry (and any arm's model factor with no matching entry) out of the experiment YAML(s) you pass, writes a LiteLLM config to <YARDSTICK_HOME>/proxy_config.yaml, and launches litellm as a detached background process on port 4000 by default.

bash 
ys proxy status
output 
proxy running (pid 48213)

Run lifecycle: start, then end

A run in yardstick has two halves. ys start claims the "active run" slot and records a new row in the database; you (or your harness) then do whatever the task calls for; ys end closes that slot out, runs the arm's success check, and prints a summary. This walkthrough doesn't drive any agent traffic through the proxy at all -- it only exercises the start/end mechanics -- so you can see the full lifecycle before adding a real harness in later tutorials.

  1. Start a run of arm-a

    experiments/example.yaml declares two arms, arm-a (marked baseline: true) and arm-b. Start a run of arm-a:

    bash 
    ys start --exp experiments/example.yaml --arm arm-a
    output 
    run a1b2c3d4  exp=mock-smoke-01  arm=arm-a  repeat=1

point your harness at the proxy:

  export ANTHROPIC_BASE_URL=http://localhost:4000
  export ANTHROPIC_API_KEY=sk-ys-demo-1234

optional request header:  x-ys-run: a1b2c3d4
the header is the precise way to attribute traffic, but harnesses like Claude Code may not let you set arbitrary headers. Without it, requests are attributed via the active-run file this command just wrote, which is correct as long as only one run is active at a time.

when the task is finished, run `ys end`

    The run id (a1b2c3d4 above) is random per run, and repeat=1 means this is the first recorded run of arm-a. ys start wrote a small JSON file at <YARDSTICK_HOME>/active.json (the "active-run state file") holding this run id, the experiment name, the arm, and a start timestamp, plus inserted a row for the run in the database.

  2. Check what's active

    At any point while a run is active, ys status just dumps the contents of that active-run state file:

    bash 
    ys status
    output 
    {
  "run_id": "a1b2c3d4",
  "experiment": "mock-smoke-01",
  "arm": "arm-a",
  "started_at": "2026-07-25T17:41:00Z"
}

  3. End the run

    Since nothing sent any requests through the proxy in this walkthrough, ending the run now will score it and print a summary where every efficiency metric is zero -- which is exactly the point of a smoke test: the whole start-to-end pipeline works, and it cost nothing, because the mock model was never even called.

    bash 
    ys end
    output 
    running success check...

run a1b2c3d4  exp=mock-smoke-01  arm=arm-a
result: SUCCESS   wall clock: 2.1s
  turns: 0
  billable_tokens: 0
  cost_usd: 0
  cache_read_ratio: 0
  context_high_water: 0
  tool_calls: 0
  tool_error_rate: 0
  redundant_tool_calls: 0
  compaction_events: 0
  active_s: 0

    ys end ran the arm's task.success_check (in example.yaml this is literally the shell command true, so it always passes), recorded the result, cleared the active-run state file, and printed the headline metrics. Every one of these is derived from rows in the requests/tool_calls tables for this run id; with no traffic recorded, they're all zero. wall_clock_s reflects real elapsed time between your ys start and ys end, so yours will differ.

Stop the proxy

When you're done, stop the background proxy process:

bash 
ys proxy down
output 
stopped process (pid 48213)

Path B -- the dashboard

ys web up runs a small FastAPI app that walks the same lifecycle as Path A -- create an experiment, start a proxy, start and end a run, browse the result -- entirely by clicking through pages in a browser. It's a thin presentation layer over the same functions the CLI calls, so it can't drift from what Path A does.

ys web up launches the dashboard as a detached background process. When you later click "start proxy" in the browser, that click calls the same proxy.proxy_up() function the CLI uses, and it reads LITELLM_MASTER_KEY from os.environ -- but os.environ inside that already-running dashboard process, not your current shell. If you export the key after starting the dashboard, the button will fail with:

output 
LITELLM_MASTER_KEY is not set. Export a key of your choosing before starting the proxy, e.g.
    export LITELLM_MASTER_KEY=sk-...
The same value is what your harness sends as its API key.

Exporting the key in your terminal afterward does nothing until you ys web down and start the dashboard again in a shell that already has it exported. So export LITELLM_MASTER_KEY before the next command.

  1. Start the dashboard

    With LITELLM_MASTER_KEY already exported in this shell:

    bash 
    ys web up
    output 
    dashboard ready at http://127.0.0.1:8501

    This launches uvicorn ys.web.app:app as its own detached process, bound to 127.0.0.1 on port 8501 by default (use ys web up --port ... for a different one) -- a separate process from the proxy, which is still port 4000. ys web up also calls the same database initialisation ys init does, so ys init is optional on this path; you don't need to run it first just to use the dashboard.

  2. Open the dashboard

    Visit http://127.0.0.1:8501. This is GET /: a list of every experiment found in ~/.yardstick/experiments/, each with its task id, arm count, and recorded run count. Right now that list is empty.

  3. Get the experiment into the dashboard

    The dashboard's list only reads YAML files that already live in ~/.yardstick/experiments/. This repo's experiments/example.yaml is not in that directory, so it will never show up on its own -- you have to either recreate it through the form (recommended, since that's the dashboard's own workflow) or copy the file in yourself.

    Option 1 -- the form. Click "new experiment" (GET /experiments/new) and fill in the same shape of data as experiments/example.yaml:

    • experiment name: mock-smoke-01 (this becomes the filename, and must match ^[A-Za-z0-9][A-Za-z0-9_-]*$)
    • task id: smoke-000, success check: true, timeout: 60
    • one model row: key probe-claude-mock, kind mock, response text This is a mock response used for yardstick smoke testing. -- a mock model row costs nothing and always returns the text you type, instead of calling Anthropic
    • two arm rows, both using model key probe-claude-mock: arm-a with the baseline checkbox ticked, and arm-b
    • repeats: 2

    Submitting posts to POST /experiments, which assembles the form fields into the same dict shape ys.experiment.Experiment validates for the CLI -- so duplicate arm ids, more than one arm marked baseline, and other structural mistakes are rejected identically to a hand-written YAML. On success it writes ~/.yardstick/experiments/mock-smoke-01.yaml and redirects you straight to the new experiment's detail page.

    Option 2 -- copy the file. If you'd rather reuse the repo's YAML verbatim:

    bash 
    cp experiments/example.yaml ~/.yardstick/experiments/mock-smoke-01.yaml

    The filename has to match the YAML's experiment: name exactly -- mock-smoke-01 here. Every dashboard link builds the file path as EXPERIMENTS_DIR/<name>.yaml, while the list view will happily show any *.yaml it finds. Copy the file in under any other name (like example.yaml) and it will appear in the list -- as mock-smoke-01, read from inside the file -- but clicking it, or any start-proxy/start-run button on it, fails with no experiment named 'mock-smoke-01', because the dashboard looks for mock-smoke-01.yaml and finds example.yaml instead. Name the copy after the experiment, not after the source file.

  4. Open the experiment

    From the list, open mock-smoke-01 (GET /experiments/mock-smoke-01). The detail page shows the task id and success check, the repeat count, a "view comparison" button, a "start proxy for this experiment" button (shown because the proxy isn't running yet), and one card per arm -- each with a "start run" button and, once there are any, a table of that arm's recorded runs (repeat number, run id, started time, success/fail/in-progress pill, wall clock, delete).

  5. Start the proxy from the experiment page

    Click "start proxy for this experiment". This posts to POST /experiments/mock-smoke-01/proxy/up, which calls the same proxy.proxy_up() as ys proxy up --exp -- but scoped to just this one experiment's models, rather than every experiment you might pass on a CLI invocation. It redirects back to the experiment page with either "proxy started" or (see the warning above) the missing-key error.

  6. Start a run on arm-a

    In the arm-a card, click "start run (repeat 1)". This posts to POST /experiments/mock-smoke-01/runs/start with the arm id, which calls the same run-start logic ys start does. It redirects back to the experiment page with a flash message showing the new run id and repeat number. From here on, every page the dashboard serves -- not just this one -- shows an "active run" card at the top, because the dashboard enforces the same single-active-run-at-a-time rule the CLI does.

  7. End the run

    Use the inline form inside that "active run" card (it's the same form on every page, including this one) to end the run -- optionally with a manual-score field that skips the success check, exactly like ys end --manual-score. Submitting posts to POST /runs/end, which calls the same runs.finish_run the CLI's ys end calls: it runs true as the success check (always passes), clears the active-run state, and redirects to the experiment page with a "run ... finished: SUCCESS" message. As with Path A, no traffic went through the proxy in this walkthrough, so every efficiency metric on the finished run is zero.

  8. View the run detail

    Back on the experiment page, click the run id in the arm-a table (GET /runs/{run_id}). It shows the run's experiment/arm/repeat and success pill, a summary card of the same headline metrics ys end prints (turns, billable_tokens, cost_usd, cache_read_ratio, context_high_water, tool_calls, tool_error_rate, redundant_tool_calls, compaction_events, active_s), plus the full per-request log and tool-call log -- both empty here, since nothing called the proxy.

  9. View the compare page

    Back on the experiment page, click "view comparison" (GET /experiments/mock-smoke-01/compare). This renders the exact same render.compare_experiment + render.render_html pipeline as ys report --html, served directly as a page instead of written to a file.

Everything in Path B has a CLI equivalent covered in tutorial 5, including the full route table, the deletion/active-run rules, and what the dashboard deliberately can't do.

Where the two paths meet

Path A and Path B are two front ends over the same state: both read and write the same SQLite database at ~/.yardstick/yardstick.db. Start a run with ys start and you'll see it appear as the dashboard's "active run" card; start one from the dashboard and ys status will print its run id from your terminal. Mixing them across one run is fine -- there's only ever one active-run slot, checked the same way from both sides.

Neither path here drove a real coding agent through the proxy -- both just exercised the start/end mechanics with the mock model. Pointing an actual agent's config at the proxy (ys harness point) is CLI-only; there's no dashboard equivalent. That's tutorial 3.

You now have a working install and have seen the full run lifecycle from both the terminal and the browser, without spending any API budget. Next up: understanding the experiment YAML itself, field by field.
