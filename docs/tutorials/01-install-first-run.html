Install and your first run

By the end of this page you'll have yardstick installed, its home directory initialised, and one complete run started and ended through the measurement proxy -- using a mocked model response, so the whole exercise costs exactly $0.

Prerequisites

You need Python 3.10 or newer and a clone of the yardstick repository. Everything below is run from the repo root.

Install

Install yardstick in editable mode. This pulls in the ys CLI (a Typer app), litellm[proxy] to run the measurement proxy, fastapi/uvicorn for the optional dashboard, and pydantic for the experiment schema.

bash 
pip install -e .

This installs the ys command itself; every step from here on is a call to ys.

Initialise yardstick's home directory

yardstick keeps all of its own state -- the SQLite database of every proxied request, the active-run marker, the generated proxy config, pid/port files -- under one directory, YARDSTICK_HOME. If you don't set that environment variable it defaults to ~/.yardstick. ys init creates that directory (and an experiments/ subdirectory inside it) and initialises the database schema.

bash 
ys init
output 
yardstick home: /home/you/.yardstick
database initialised

"/home/you/.yardstick" will actually print as your own home directory, expanded from ~/.yardstick (or wherever YARDSTICK_HOME points, if you've set it). The database file itself lands at <YARDSTICK_HOME>/yardstick.db.

Choose a master key

Before starting the proxy you need a LITELLM_MASTER_KEY. This is not a key anyone issues you -- it's a shared secret you make up yourself, that authenticates your local harness to your local proxy. LiteLLM's proxy reads it as general_settings.master_key (yardstick generates that into the proxy config as os.environ/LITELLM_MASTER_KEY), and rejects any request that doesn't send it as a bearer token.

The exact same value has to be exported wherever you run ys proxy up and wherever you later run ys harness point (covered in tutorial 3) -- the harness sends this value back to the proxy as its API key, so a mismatch just looks like an auth failure. Pick one string and export it once per shell session.

bash 
export LITELLM_MASTER_KEY=sk-ys-demo-1234

Start the proxy against the mock experiment

experiments/example.yaml is a smoke-test experiment shipped in the repo. Its single model, probe-claude-mock, is configured with litellm's mock_response field -- every request served under that model name gets back a canned string instead of ever reaching Anthropic. That's exactly what makes it safe to run end-to-end for free.

bash 
ys proxy up --exp experiments/example.yaml
output 
proxy ready at http://localhost:4000

Under the hood this reads every models: entry (and any arm's model factor with no matching entry) out of the experiment YAML(s) you pass, writes a LiteLLM config to <YARDSTICK_HOME>/proxy_config.yaml, and launches litellm as a detached background process on port 4000 by default.

bash 
ys proxy status
output 
proxy running (pid 48213)

Run lifecycle: start, then end

A run in yardstick has two halves. ys start claims the "active run" slot and records a new row in the database; you (or your harness) then do whatever the task calls for; ys end closes that slot out, runs the arm's success check, and prints a summary. This walkthrough doesn't drive any agent traffic through the proxy at all -- it only exercises the start/end mechanics -- so you can see the full lifecycle before adding a real harness in later tutorials.

  1. Start a run of arm-a

    experiments/example.yaml declares two arms, arm-a (marked baseline: true) and arm-b. Start a run of arm-a:

    bash 
    ys start --exp experiments/example.yaml --arm arm-a
    output 
    run a1b2c3d4  exp=mock-smoke-01  arm=arm-a  repeat=1

point your harness at the proxy:

  export ANTHROPIC_BASE_URL=http://localhost:4000
  export ANTHROPIC_API_KEY=sk-ys-demo-1234

optional request header:  x-ys-run: a1b2c3d4
the header is the precise way to attribute traffic, but harnesses like Claude Code may not let you set arbitrary headers. Without it, requests are attributed via the active-run file this command just wrote, which is correct as long as only one run is active at a time.

when the task is finished, run `ys end`

    The run id (a1b2c3d4 above) is random per run, and repeat=1 means this is the first recorded run of arm-a -- start it again later and you'll see repeat=2, and so on. What ys start actually did is write a small JSON file at <YARDSTICK_HOME>/active.json (the "active-run state file") holding this run id, the experiment name, the arm, and a start timestamp, plus insert a row for the run in the database. It's this file, not anything printed to your terminal, that ys end and ys status read from.

  2. Check what's active

    At any point while a run is active, ys status just dumps the contents of that active-run state file:

    bash 
    ys status
    output 
    {
  "run_id": "a1b2c3d4",
  "experiment": "mock-smoke-01",
  "arm": "arm-a",
  "started_at": "2026-07-25T17:41:00Z"
}

  3. End the run

    Since nothing sent any requests through the proxy in this walkthrough, ending the run now will score it and print a summary where every efficiency metric is zero -- which is exactly the point of a smoke test: the whole start-to-end pipeline works, and it cost nothing, because the mock model was never even called.

    bash 
    ys end
    output 
    running success check...

run a1b2c3d4  exp=mock-smoke-01  arm=arm-a
result: SUCCESS   wall clock: 2.1s
  turns: 0
  billable_tokens: 0
  cost_usd: 0
  cache_read_ratio: 0
  context_high_water: 0
  tool_calls: 0
  tool_error_rate: 0
  redundant_tool_calls: 0
  compaction_events: 0
  active_s: 0

    ys end ran the arm's task.success_check (in example.yaml this is literally the shell command true, so it always passes), recorded the result, cleared the active-run state file, and printed the headline metrics -- turns, billable_tokens, cost_usd, cache_read_ratio, context_high_water, tool_calls, tool_error_rate, redundant_tool_calls, compaction_events, and active_s. Every one of these is derived from rows in the requests/tool_calls tables for this run id; with no traffic recorded, they're all zero. wall_clock_s reflects real elapsed time between your ys start and ys end, so yours will differ.

In tutorial 3 you'll point a real Claude Code session at the proxy so these same metrics reflect an actual agent session instead of all zeros.

Stop the proxy

When you're done, stop the background proxy process:

bash 
ys proxy down
output 
stopped process (pid 48213)

You now have a working install and have seen every stage of the run lifecycle without spending any API budget. Next up: understanding the experiment YAML itself, field by field.
