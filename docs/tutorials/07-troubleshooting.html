Troubleshooting

Every entry below is organized problem → cause → fix, and is grounded in an error message yardstick actually raises or a fallback its metrics code actually takes -- not a guess at what might go wrong.

Diagnostic checklist

Before digging into a specific symptom, run these five commands. Together they tell you whether the proxy is up, whether your harness is really pointed at it, whether a run is active, and whether the dashboard (if you use it) is running.

bash 
ys status           # is a run currently active? which experiment/arm?
ys proxy status      # is the measurement proxy running, and on what pid?
ys harness status    # is claude-code (or opencode) actually pointed at the proxy?
ys web status        # is the dashboard running, if you use it?
tail -n 50 ~/.yardstick/proxy.log   # the proxy's own stdout/stderr

The proxy log is the single most useful file when a run looks empty or the proxy won't start -- it's where litellm's own startup errors, auth failures, and per-request tracebacks from yardstick's collector all land (see procutil.launch_detached, which redirects the proxy subprocess's stdout/stderr into that file).

LITELLM_MASTER_KEY problems

ys proxy up and ys harness point both need LITELLM_MASTER_KEY exported in the shell that runs them, and it must be the same value in both places.

  • ys proxy up with the variable unset -- exits 1 with: "LITELLM_MASTER_KEY is not set. Export a key of your choosing before starting the proxy...". Fix: export a key first, e.g. export LITELLM_MASTER_KEY=sk-..., then re-run ys proxy up.
  • ys harness point with the variable unset -- exits 1 with: "LITELLM_MASTER_KEY is not set -- export the same key you started `ys proxy up` with." This is a separate check in the CLI (not the proxy's), because pointing a harness needs the key too -- it's written into the harness config as the API key the harness will send.
  • mismatched keys -- if the shell you ran ys proxy up in exported one value and the shell you ran ys harness point in exported a different one (or none, picked up from a stale terminal), the harness config ends up with an API key the proxy's general_settings.master_key doesn't accept. The proxy will reject every request with an auth error -- check ~/.yardstick/proxy.log for 401s. There's no cross-check in the code for this; the two commands just don't share state beyond the environment variable.

Export LITELLM_MASTER_KEY once per terminal session before running either command, so both commands definitely see the same value.

"no active run" and blocked starts

ys start and ys end both work against a single active-run slot recorded in ~/.yardstick/active.json.

  • ys end with nothing active -- exits 1 with no active run. Start one with `ys start`. This is runs.NoActiveRun, raised when ~/.yardstick/active.json doesn't exist.
  • ys start while a run is already active -- fails with state.RunAlreadyActive: "run <id> (exp=..., arm=...) is already active. Use --force to override, or `ys end` it first." The safe fix is to finish the in-flight run with ys end. The override is ys start ... --force.

--force overwrites the active-run file but does not end the run it replaces -- that older run's database row is left with no ended_at, no wall_clock_s, and no task_success. It will still show up in ys compare as an unfinished repeat with mostly empty metrics. Only reach for --force if you know the previous run's active-run file is stale (e.g. from a crashed session) -- otherwise ys end the real run first.

There's also no active-run row without a database row problem: if the run pointed to by active.json was deleted from the database (directly, or somehow lost), ys end fails with runs.ActiveRunMissingDbRow: "run <id> is active but has no database row". There is no dedicated command to clear the active-run file on its own -- the way out is ys start ... --force against any experiment/arm (which overwrites active.json with a fresh, valid run), followed by a normal ys end.

Stale pidfiles

The proxy and dashboard are both started as detached background processes via procutil.launch_detached, which writes the child's pid to a pidfile (proxy.pid / web.pid) and its port to a matching port file. Status checks read the pidfile and then ask the OS whether that pid is still alive (procutil.alive, which sends signal 0 via os.kill).

A pidfile is "stale" when the file exists but the process it names is gone -- e.g. the machine rebooted, or the process was killed outside of ys proxy down. ys proxy status and ys web status distinguish this from "never started":

Situation What ys proxy status prints
No pidfile at all proxy not running
Pidfile exists, process is alive proxy running (pid N)
Pidfile exists, process is gone proxy not running (stale pidfile, pid N)

ys web status follows the identical pattern for the dashboard. A stale pidfile is harmless to leave around, but ys proxy up and ys web up only refuse to start when the recorded pid is genuinely alive -- so a stale pidfile does not block a fresh ys proxy up. If you do want to clear it explicitly, run ys proxy down (or ys web down): both detect the "already gone" case and remove the pidfile and port file, printing process (pid N) was already gone; removed stale pidfile.

Port conflicts

The proxy defaults to port 4000, the dashboard to port 8501. If something else on the machine already owns that port, litellm or uvicorn will fail to bind and the child process exits quickly -- ys proxy up / ys web up then time out waiting for the readiness check and report: "proxy (pid N) did not become ready within 15s. Check the log at ~/.yardstick/proxy.log" (or the equivalent dashboard message pointing at web.log). The log will show the real bind error (e.g. "address already in use").

Fix it with the --port flag on either command, e.g. ys proxy up --exp experiments/example.yaml --port 4100 or ys web up --port 8600. ys start reads back whichever port the proxy was actually started on (from ~/.yardstick/proxy.port) when it prints the ANTHROPIC_BASE_URL to export, so you don't have to remember a non-default port yourself.

A run recorded no requests

If you drive the agent through a whole task and then run ys end, but the printed metrics are all zero or missing, the most likely cause is that no requests actually landed in requests for that run's id. Every metric that sums or counts requests degrades to an empty-run default rather than erroring: turns is 0, cost_usd is 0.0, context_high_water is 0, tool_calls/tool_error_rate are 0/0.0, and cache_read_ratio is 0.0 (see ys/metrics.py's token_metrics, overhead_metrics, and tool_call_metrics, all of which special-case the no-requests case explicitly rather than dividing by zero).

Usual causes, in order of likelihood:

  • The harness was never actually pointed at the proxy. Run ys harness status -- if it reports not pointed, ys harness point either wasn't run, or was run for a different agent than the one you actually drove.
  • ANTHROPIC_BASE_URL (and ANTHROPIC_API_KEY) weren't exported in the same shell that launched the agent. ys harness point rewrites the agent's on-disk config, but some agents/setups also read these from the environment at process start -- if the shell that launched the agent doesn't have them exported, it can end up talking to the real Anthropic API directly rather than the proxy, and nothing gets logged. This is exactly what ys start prints the export ANTHROPIC_BASE_URL=... / export ANTHROPIC_API_KEY=... lines for -- see tutorial 3.
  • Traffic was attributed to a different run. See the next section -- the requests may well have been logged, just under another run's id (or under unattributed).

Check ~/.yardstick/proxy.log too -- if the proxy never received any HTTP requests at all, that's conclusive evidence the harness wasn't actually talking to it.

Attribution going wrong

Requests are attributed to a run in one of two ways (see ys/collector.py's _resolve_run_id): the x-ys-run request header, if the harness sends one, or -- failing that -- whatever run id is currently written in ~/.yardstick/active.json. Header-based attribution is precise; file-based attribution is a best-effort fallback that is only correct as long as exactly one run is active at a time (see tutorial 3 and the README's Attribution section).

Two situations break it:

  • Two runs active "at once." Normally ys start refuses a second run (RunAlreadyActive), but --force lets you override it. If you do that while the first run's agent process is still making requests, those late requests get attributed to whichever run is currently active in active.json -- i.e. the new one -- silently corrupting both runs' numbers.
  • A stale active.json. If a run ends abnormally (process killed, machine crash) without ys end running, active.json is never cleared. Any proxy traffic that arrives afterwards -- from an unrelated later session that forgot to run ys start again, for instance -- gets attributed to that old, already-dead run id. Conversely, if the run id in a stale active.json doesn't match any row in the runs table (e.g. the run was deleted with ys delete), the collector's write path detects the missing row and falls back to logging the request under the special unattributed run id (see _write's explicit re-check in ys/collector.py) rather than dropping the data or attributing it to a stray id that doesn't exist.

Run ys status before starting a new run in a shell you haven't used in a while. If it reports an active run you don't recognize, either ys end it (if it's real) or use ys start --force deliberately -- don't assume active.json is clean.

ys end fails: no usable success_check

ys end runs the active arm's task.success_check shell command and uses its exit code to decide success/fail. If the experiment YAML has no success_check at all, ys end exits 1 with runs.NoSuccessCheck's message, followed by the CLI's own hint: "experiment has no task.success_check; finish with a manual score instead (re-run with --manual-score)."

The escape hatch is exactly what the message says: ys end --manual-score <value>. Any score > 0 is recorded as success, anything ≤ 0 as failure -- manual_score itself is also stored on the run row so it's visible later. Manual scoring skips running success_check entirely, even if one is present in the YAML.

Recovering a harness config

ys harness point snapshots an agent's config exactly once, the first time it touches that agent -- into a manifest under ~/.yardstick/harness_backups/<agent>.json. That manifest records the original file's exact bytes (or the fact that no file existed yet), and it never moves, even across repeated point calls with different ports/keys. ys harness reset <agent> always restores from that manifest -- never from whatever point last wrote -- and either rewrites the original bytes verbatim, or deletes the config file if it didn't exist before yardstick touched it.

  • ys harness reset with no prior point -- fails with HarnessError: "no backup found for '<agent>' -- `ys harness point` was never run for it (or the backup dir was cleared), so there's nothing to restore." There is nothing to restore to; the config, if pointed at all, was pointed by something other than yardstick.
  • Hand-editing the config after point. ys harness point only understands strict JSON -- no // comments, no trailing commas. If you (or another tool) leave the file as JSON with comments (this matters especially for opencode's .jsonc), the next ys harness point or ys harness status call fails/degrades: point raises HarnessError -- "<path> is not strict JSON (comments/trailing commas aren't supported by yardstick's merge) -- <details>. Edit it by hand instead, or remove comments temporarily." ys harness status instead just reports not pointed for that agent, because it silently swallows the same parse error rather than raising through the status command.

If ys harness reset fails (no backup) while your agent's real config is still pointed at a proxy you've since torn down with ys proxy down, your agent is now configured to talk to a dead localhost proxy and will fail every request until you fix the config by hand. Run ys harness status to confirm what's actually on disk before assuming a reset succeeded.

Where to look when nothing else helps

Everything yardstick writes lives under YARDSTICK_HOME (default ~/.yardstick, overridable via the YARDSTICK_HOME environment variable -- see ys/paths.py). When metrics look wrong, a command hangs, or a status check disagrees with what you expect, these are the files to open directly.

File What it holds
yardstick.db SQLite database -- experiments, arms, runs, requests, tool_calls. The source of truth for every metric.
active.json The currently active run (run id, experiment, arm, started_at), or absent if no run is active. Deleted by ys end.
proxy_config.yaml The generated LiteLLM config ys proxy up wrote from your experiment YAML(s) -- model list, callback, master key setting.
proxy.pid / proxy.port / proxy.log The proxy's pid, listening port, and stdout/stderr. Check the log first for startup failures, bind errors, and auth rejections.
web.pid / web.port / web.log Same, for the dashboard (ys web up).
experiments/ Directory ensure_home() creates alongside the rest of YARDSTICK_HOME.
harness_backups/<agent>.json The one-time-snapshot manifest ys harness reset restores from.

ys compare / ys report erroring or empty

Both commands call the same aggregation (render.compare_experiment) and raise render.CompareError in two situations:

  • No recorded runs for any arm. "no runs found for any arm of experiment '<name>'. Run `ys start` / `ys end` at least once per arm first." -- by far the most common cause: you ran ys compare against an experiment id that has never completed a full ys start/ys end cycle (or the experiment id in the YAML doesn't match what earlier runs were recorded under).
  • Task drift. If the database already has an experiment row recorded with a different task.id than the YAML you're comparing now, ys compare refuses outright: "stored experiment '<name>' was last run with task.id='<old>', but the YAML you're comparing now has task.id='<new>'. Refusing to compare -- these are not the same fixed task." This guards against silently comparing runs of two different tasks as if they were arms of the same experiment.

This check only compares against the YAML you pass to ys compare right now, not against what each historical run actually executed at the time (ys start overwrites the stored config_yaml/task_json on every run) -- see the module docstring in ys/render.py for the known limitation.

Publishing these docs

This site is deployed by .github/workflows/pages.yml, which publishes the contents of docs/ to GitHub Pages on every push to main that touches docs/** (or the workflow itself), and on manual dispatch. The one-time repository setting required for this to work is under Settings → Pages → Source: GitHub Actions -- without it, the workflow's deploy job has nothing to publish to. Once that's set, the live site is at https://allannapier.github.io/yardstick/.

docs/.nojekyll exists so GitHub Pages serves every file exactly as committed, with no Jekyll build step in between -- without it, Jekyll's default processing skips any file or directory whose name starts with an underscore, which would silently drop docs/_template.html (and any future _-prefixed asset) from the published site.

Because the site is served from the /yardstick/ subpath rather than the domain root, every link and asset reference across these pages is relative (../assets/site.css, ../tutorials/NN-name.html, and so on) -- see docs/CONTRACT.md section 2. An absolute path like /assets/site.css would resolve against the domain root and 404.
