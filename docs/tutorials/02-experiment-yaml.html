Designing an experiment

Every yardstick experiment is one YAML file: a task, one or more models, a set of arms to compare, and the metrics you care about. This page goes through every field in that schema, the two validation rules most likely to trip you up, and what makes a comparison actually meaningful.

Where the schema lives

The experiment shape is defined as pydantic models in ys/experiment.py. ys.experiment.load_experiment(path) reads the YAML and validates it against the Experiment model; every field below comes directly from that file, not from a separate spec doc, so it can't drift out of sync with what the CLI actually accepts.

Top-level fields

Field Type Required Default Meaning
experiment string yes — Identifies the experiment. Used as the primary key for the experiments table and as the exp= label printed by ys start/ys end.
question string no None Free-text statement of what the experiment is trying to answer. Purely documentation -- stored alongside the experiment row.
task Task yes — The single task every arm runs (see below).
factors dict[str, list[str]] no {} Documents the dimensions you're varying (e.g. agent, model) and the values in play. Arms reference these values in their own factors map; nothing enforces that an arm's factor values actually appear in this list.
models dict[str, dict] no {} Maps a factors.model value to the LiteLLM litellm_params ys proxy up should generate for it. See the dedicated section below.
arms list[Arm] yes — The arms being compared. Must be non-empty; ids must be unique (enforced, see validation below).
repeats int no 3 How many times you intend to run each arm. Not enforced by the CLI (nothing stops you running an arm more or fewer times) -- it's a target for how many repeats to actually run and aggregate over.
metrics Metrics no see below Which metrics to gate on and report (see below).

task fields

Field Type Required Default Meaning
id string yes — Identifier for the task.
repo string no None Repository the task operates in. Documentation only in the schema -- yardstick itself doesn't clone or check it out for you.
ref string no None Git ref (branch/commit) the task starts from. Same caveat as repo.
prompt_file string no None Path to the file containing the task prompt you'll give the agent.
success_check string yes — A shell command. ys end runs it (via subprocess.run(..., shell=True)) and treats a zero exit code as success. If empty/omitted, ys end refuses unless you pass --manual-score.
timeout_s int no 1800 Timeout in seconds for success_check. If it's exceeded, the run is scored as failed and the recorded output notes the timeout.

arms[] fields

Field Type Required Default Meaning
id string yes — The value you pass to ys start --arm. Must be unique across the experiment's arms.
factors dict[str, str] yes — This arm's concrete factor values, e.g. {agent: claude-code, model: probe-claude-mock}. The model value is what ys proxy up uses to resolve litellm_params against models:.
notes string no None Free-text annotation, stored with the arm row.
baseline bool no False Marks this arm as the control for comparison. At most one arm may set this (see validation below).

metrics fields

Field Type Required Default Meaning
gate string no "task_success" Which condition a run must pass to count toward the aggregated efficiency numbers for its arm.
primary list[str] no [] The headline metrics you most care about for this experiment (e.g. cost_usd, turns).
secondary list[str] no [] Supporting metrics worth reporting but not the headline.
derived list[str] no [] Metrics computed from other metrics (e.g. cost_per_success, tokens_per_turn).

Nothing in ys/experiment.py validates that the metric names in primary/secondary/derived are real, known metric keys -- they're just strings that a renderer (ys compare/ys report) looks up later.

The two validation rules that will actually bite you

Experiment has two validators, and both raise a pydantic ValueError at load time (i.e. as soon as you run any ys command that touches this YAML) if violated:

  • At least one arm is required, and arm ids must be unique. The _non_empty_arms field validator rejects an empty arms: list with "experiment must declare at least one arm", and rejects duplicate ids with "duplicate arm ids: [...]".
  • At most one arm may set baseline: true. The _exactly_one_baseline model validator only objects when more than one arm claims the baseline -- despite its name, zero baseline arms is fine (baseline_arm() just returns None). Two or more raises "more than one baseline arm declared: [...]".

The models: map, carefully

models: is not part of some external experiment spec -- the comment above it in ys/experiment.py is explicit that it was added because ys proxy up needs a concrete source of LiteLLM parameters for each model name, and nothing else in the schema provided one. It maps a factors.model value (the string an arm uses in its own factors.model) to the litellm_params dict that ends up in the generated proxy's model_list.

Two shapes show up in the shipped examples:

  • A mock double. In experiments/example.yaml, probe-claude-mock maps to {model: anthropic/claude-3-5-sonnet-20241022, mock_response: "..."}. LiteLLM's mock_response field short-circuits the call and returns that canned string instead of contacting Anthropic -- this is what makes tutorial 1's smoke test free.
  • A real deployment. In experiments/interactive-sonnet.yaml, claude-sonnet-5 maps to {model: claude-sonnet-5, api_key: os.environ/ANTHROPIC_API_KEY}. The os.environ/... value is LiteLLM's own syntax for "read this from an environment variable at request time" rather than a literal string baked into the generated config file.

If an arm's factors.model value has no matching entry under models:, ys proxy up doesn't error -- it falls back to a convention, generating {model: anthropic/<value>, api_key: os.environ/ANTHROPIC_API_KEY} for it (this is exactly what ys/proxy.py's _fallback_params does). In other words: an unrecognized model factor is assumed to be an Anthropic model name, proxied with whatever ANTHROPIC_API_KEY is set in the proxy process's environment.

ys proxy up raises if no model resolves at all across the experiment(s) you pass it: "no models resolved from the given experiments -- each arm needs a model factor, or the experiment needs a models: block."

Designing a good comparison

A few practices fall directly out of how ys compare aggregates runs (see ys/metrics.py's aggregate_run_metrics):

  • Change one factor at a time between the arms you want to compare. If two arms differ in both model and agent, you can't attribute a cost or turns difference to either one specifically.
  • Mark your control arm baseline: true. It's how a reader (and later, ys compare/ys report) knows which arm the others are measured against.
  • repeats matters because aggregation is a mean over gate-passing runs, not a single sample. Per arm, aggregate_run_metrics takes every run's task_success as the default gate, then averages (and computes population stdev of) each efficiency metric only across the runs that passed. An arm you only ran once gives you no signal on how consistent its cost or turn count actually is; an arm that's cheap on one run and expensive on the next needs enough repeats for that spread to show up rather than being silently hidden behind a single lucky (or unlucky) run.

Annotated examples

experiments/example.yaml -- the mock smoke test

experiments/example.yaml 
experiment: mock-smoke-01
question: >
  Does the mock harness pipeline work end to end without spending real API budget?

task:
  id: smoke-000
  success_check: "true"          # always succeeds -- this experiment is about plumbing, not task quality
  timeout_s: 60

factors:
  agent: [claude-code]
  model: [probe-claude-mock]

models:
  probe-claude-mock:
    model: anthropic/claude-3-5-sonnet-20241022
    mock_response: "This is a mock response used for yardstick smoke testing."

arms:
  - id: arm-a
    factors: {agent: claude-code, model: probe-claude-mock}
    notes: "baseline mock arm"
    baseline: true               # the one arm marked baseline
  - id: arm-b
    factors: {agent: claude-code, model: probe-claude-mock}
    notes: "second mock arm, deliberately noisier"

repeats: 2

metrics:
  gate: task_success
  primary: [cost_usd, billable_tokens, turns, wall_clock_s]
  secondary: [tool_calls, redundant_tool_calls, tool_error_rate, cache_read_ratio, fixed_overhead_tokens, context_high_water, compaction_events]
  derived: [cost_per_success, tokens_per_turn]

experiments/interactive-sonnet.yaml -- a real-model interactive arm

experiments/interactive-sonnet.yaml 
experiment: interactive-sonnet-01
question: >
  Ad-hoc arm for routing an interactive Claude Code session through the ys
  proxy against the real claude-sonnet-5 model (spends real API budget --
  kept separate from example.yaml's mock smoke test on purpose).

task:
  id: interactive-000
  success_check: "true"          # no automated check for this task -- expect --manual-score at `ys end`
  timeout_s: 3600

factors:
  agent: [claude-code]
  model: [claude-sonnet-5]

models:
  claude-sonnet-5:
    model: claude-sonnet-5
    api_key: os.environ/ANTHROPIC_API_KEY   # LiteLLM env-var indirection, not a literal key in the file

arms:
  - id: arm-sonnet
    factors: {agent: claude-code, model: claude-sonnet-5}
    notes: "real Sonnet 5 -- spends real API budget"
    baseline: true

repeats: 1                       # this experiment only defines one arm to run

metrics:
  gate: task_success
  primary: [cost_usd, billable_tokens, turns, wall_clock_s]
  secondary: [tool_calls, redundant_tool_calls, tool_error_rate, cache_read_ratio, fixed_overhead_tokens, context_high_water, compaction_events]
  derived: [cost_per_success, tokens_per_turn]
