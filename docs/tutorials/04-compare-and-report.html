Comparing arms and reporting

Once every arm of an experiment has at least one recorded run, ys compare and ys report aggregate those runs into a table you can read at a glance -- this page explains exactly what each number means and where the subtleties are.

The two commands

Both read the same already-recorded runs from ~/.yardstick/yardstick.db; neither one runs anything or talks to a model.

bash 
ys compare --exp experiments/example.yaml
ys report  --exp experiments/example.yaml --html report.html

ys compare prints a Rich table straight to the terminal. ys report computes the same comparison and writes it out as a single self-contained HTML file -- no external stylesheets, scripts, or fonts, so it opens correctly straight from disk, can be emailed as an attachment, or committed alongside a PR as a record of what a change did to the numbers.

How runs are grouped into arms

Every run is stored under an arm row id of the form {experiment}::{arm}. ys compare/ys report pull all recorded run ids for each arm in the experiment YAML, skip any arm with zero runs, and sort the results so the baseline arm (the one arm with baseline: true in the YAML, if any) comes first -- every other arm follows in alphabetical order by arm id. The baseline's column header gets a trailing * so you can always tell which column the percentage deltas are measured against.

If no arm in the experiment has any recorded runs yet, both commands fail with an error telling you to run ys start / ys end at least once per arm first.

The gate: which runs count as a "success"

Before anything is averaged, every run in an arm is passed through a gate -- by default, a run passes the gate if its task_success flag (set by ys end from the arm's success_check) is true. This is the subtlest part of reading the table:

  • Every run in the arm counts toward n_runs and toward the success count/rate, whether it passed the gate or not.
  • Only gate-passing runs contribute to the mean and spread of every efficiency metric (cost, tokens, turns, tool calls, and so on). A failed run's cost, token counts, and turn count are excluded from those averages entirely.

The reasoning, straight from aggregate_run_metrics's docstring: an arm that's cheap but fails half the time should not look cheap. If failed runs were folded into the efficiency means, an arm that gives up after one cheap turn would drag its own average cost down and look like a bargain -- even though it didn't finish the task.

cost_per_success

cost_per_success is deliberately computed differently from the other metrics: it sums cost_usd over all of the arm's runs -- successful or not, because a failed run still spent real money on tokens -- and divides by the count of successful runs. If an arm has zero successes, cost_per_success is None (shown as -) rather than a divide-by-zero.

Spread is population standard deviation

The "spread" shown next to a mean (in the HTML report; the terminal table doesn't show it, see below) is statistics.pstdev over the gate-passing runs' values for that metric. Population stdev is 0.0 for a single observation rather than undefined, which is what keeps a repeats: 1 arm's row usable instead of blank. One wrinkle: the HTML report only prints the ± spread (n=...) annotation when more than one run contributed (n > 1) -- so a single-success arm's cell shows a bare mean with no ±, even though the spread value being suppressed is 0.0, not missing.

Percentage deltas against the baseline

Every non-baseline arm's row also shows a percentage delta against the baseline arm's mean for that metric: (value - baseline) / abs(baseline) * 100. _delta_str renders nothing at all -- not 0%, not a dash, just an empty string -- when the baseline's mean is missing (no gate-passing runs for that metric) or exactly zero, since a percentage change against zero is meaningless. You'll see this in the example below: tool_error_rate and compaction_events both start at 0 for the baseline arm, so the comparison arm's values for those two rows carry no delta at all, even though something clearly changed.

The fingerprint-drift signal

_fingerprint_drifted checks, for any arm with two or more repeats, whether the (model, toolset_hash, system_prompt_hash) triple recorded on each run actually stayed the same across every repeat (a run whose fingerprint is still unset -- no requests logged yet -- isn't counted as drift, just as not-yet-observed). If more than one distinct triple shows up among an arm's repeats, that arm is flagged: its header gets [UNCONTROLLED] appended in the terminal table, or an UNCONTROLLED badge in the HTML report.

This is a broken-control warning, not a metrics warning: it means the repeats you're averaging together didn't actually run the same treatment. A common cause is editing ~/.claude/settings.json or the experiment's model config mid-experiment, or pointing a harness at a different model between repeats without realizing the arm's factor value didn't change accordingly.

ys compare/ys report also refuse to compare at all if the experiment already has a database row recorded under a different task.id than the YAML you're pointing --exp at now. This guardrail only checks the experiment's stored task against the current YAML, though -- it can't detect that some individual historical run actually executed a since-changed task, since ys start overwrites the stored config/task on every run. Keep task.id stable for the life of an experiment rather than relying on this check to catch drift after the fact.

What the HTML report adds

ys report --html renders the identical comparison table plus a per-run detail section the terminal can't show. For every run of every arm it draws two small inline SVGs, computed straight from that run's requests:

  • Context sparkline -- a polyline of input + cache_creation + cache_read tokens for each request in the run, in turn order, scaled to that run's own min/max so the shape of context growth is visible regardless of the run's absolute size. Shown as "not enough data" for a run with fewer than two requests.
  • Compaction timeline -- one colored bar per request, colored by that request's transition classification (continuation, compaction, branch, reset, or gray for a request with nothing to compare against). A quick visual read of when and how often a run's context got reset or summarized -- see the metrics reference for what each transition means.

Because the report is one self-contained HTML string with everything inlined -- no external CSS, JS, fonts, or images -- it's safe to open directly from disk, attach to an email, or commit into a repo as a durable snapshot of a comparison. There's nothing else to ship alongside it.
