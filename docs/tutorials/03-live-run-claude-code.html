Measuring a live Claude Code session

This is the tutorial that spends real API budget: pointing an actual Claude Code session at the yardstick proxy, driving a task through it, and getting back real cost/token/turn numbers instead of the all-zero smoke test from tutorial 1.

This walkthrough uses experiments/interactive-sonnet.yaml, which routes traffic to the real claude-sonnet-5 model (see tutorial 2 for a full field-by-field read of that file). Make sure the proxy is up first -- ys proxy up --exp experiments/interactive-sonnet.yaml, with LITELLM_MASTER_KEY exported, exactly as in tutorial 1.

Point Claude Code at the proxy

ys harness point rewrites the config file of a supported agent so it talks to the local proxy instead of the real API. Two agents are supported today, claude-code and opencode; this tutorial uses claude-code.

bash 
export LITELLM_MASTER_KEY=sk-ys-demo-1234
ys harness point claude-code
output 
claude-code: pointed at http://localhost:4000 (/home/you/.claude/settings.json)

For claude-code, the file it rewrites is ~/.claude/settings.json. It deep-sets two keys inside it -- env.ANTHROPIC_BASE_URL to http://localhost:<port>, and env.ANTHROPIC_API_KEY to the key you pass it -- while leaving every other key in the file untouched (it loads the file as strict JSON, sets just those two paths, and writes the whole object back).

LITELLM_MASTER_KEY must be exported in the shell you run ys harness point from. If it isn't set, the command prints "LITELLM_MASTER_KEY is not set -- export the same key you started `ys proxy up` with." and exits with status 1 -- it never writes to your config in that case.

The backup, and why it only happens once

The very first time ys harness point touches a given agent's config, it snapshots the file's exact original bytes (or the fact that the file didn't exist at all) into a manifest at <YARDSTICK_HOME>/harness_backups/<agent>.json before writing anything. Every later call to point -- even with a different port or key -- leaves that manifest alone; only ys harness reset reads from it. That's deliberate: repeated point/reset cycles can't drift what "the original config" means away from what was really there before yardstick touched anything.

Check what's pointed

bash 
ys harness status claude-code
output 
claude-code: pointed at proxy  (backup available)  -- /home/you/.claude/settings.json

Run it with no argument (or ys harness status all) to check every supported agent at once.

Attribution: how a request gets tied to a run

Once the proxy is serving traffic, yardstick still needs to know which run each request belongs to. ys start prints an x-ys-run: <run_id> header for exactly this purpose -- when a harness supports sending custom headers on its API requests, this is the precise attribution mechanism.

Claude Code, though, doesn't give you a way to set an arbitrary header on its outgoing requests. So when that header isn't present, yardstick falls back to attributing every incoming request to whatever run is currently marked active in <YARDSTICK_HOME>/active.json -- the same file ys start writes and ys status reads.

This fallback is correct only as long as exactly one run is active at a time. If you (or a script) start a second run while a Claude Code session from a first run is still producing traffic, every request from either session with no x-ys-run header gets attributed to whichever run is currently active in the state file -- silently mixing the two runs' requests together. Don't start a new run until you've ended the previous one.

Export the proxy environment and start the run

bash 
ys start --exp experiments/interactive-sonnet.yaml --arm arm-sonnet
output 
run 7f3e9a02  exp=interactive-sonnet-01  arm=arm-sonnet  repeat=1

point your harness at the proxy:

  export ANTHROPIC_BASE_URL=http://localhost:4000
  export ANTHROPIC_API_KEY=sk-ys-demo-1234

optional request header:  x-ys-run: 7f3e9a02
the header is the precise way to attribute traffic, but harnesses like Claude Code may not let you set arbitrary headers. Without it, requests are attributed via the active-run file this command just wrote, which is correct as long as only one run is active at a time.

when the task is finished, run `ys end`

Since Claude Code was already pointed at the proxy by ys harness point (which wrote ANTHROPIC_BASE_URL/ANTHROPIC_API_KEY straight into ~/.claude/settings.json), you don't strictly need to re-export those two lines yourself for Claude Code specifically -- they're printed because ys start doesn't know which harness you're using, and for a harness that reads its API config from the environment rather than a settings file, exporting them is exactly what you'd do next.

Drive the agent through the task

With the proxy up, Claude Code pointed at it, and a run active, open Claude Code and work the task normally -- every request it sends now flows through the proxy and gets logged against this run id (via the active-run fallback described above, since Claude Code can't set the x-ys-run header itself).

End the run

interactive-sonnet.yaml's success_check is just "true" -- a placeholder, not a meaningful automated check for whatever real task you actually gave the agent. For a task like this, score it by hand with --manual-score instead of trusting the check:

bash 
ys end --manual-score 1

A --manual-score greater than 0 records the run as a success; otherwise it's recorded as a failure. If you omit --manual-score, ys end runs task.success_check as a shell command and gates on its exit code instead -- fine for example.yaml's smoke test, not meaningful here since the check is just true.

output 
run 7f3e9a02  exp=interactive-sonnet-01  arm=arm-sonnet
result: SUCCESS   wall clock: 612.4s
  turns: 14
  billable_tokens: 48210
  cost_usd: 0.3821
  cache_read_ratio: 0.71
  context_high_water: 9840
  tool_calls: 22
  tool_error_rate: 0.045
  redundant_tool_calls: 3
  compaction_events: 0
  active_s: 58.2

The numbers above are illustrative only -- your actual turns, cost_usd, and other metrics depend entirely on the task you gave the agent and how long the session ran. Unlike tutorial 1's mock run, these come from real requests logged by the proxy's collector.

Clean up: reset the harness

Do not skip this step. As long as Claude Code's config still points at http://localhost:4000, every Claude Code session on this machine -- including ones with no yardstick run active -- keeps routing through the proxy, and fails outright once you run ys proxy down. Restore the real config before you're done for the session:

bash 
ys harness reset claude-code
output 
claude-code: restored (/home/you/.claude/settings.json)

reset always restores from the original snapshot taken the first time point ran for this agent -- never from whatever point last wrote -- so it puts back exactly what was there before yardstick touched anything (including deleting the file entirely, if it didn't exist before). If no backup manifest exists yet -- because point was never run for this agent, or the backup directory was cleared -- reset raises rather than guessing: "no backup found for 'claude-code' -- `ys harness point` was never run for it (or the backup dir was cleared), so there's nothing to restore."

Overriding a stale active run

If a previous session ended without running ys end (a crash, a forgotten cleanup step), the active-run state file is still sitting there, and a plain ys start refuses: "run <id> (exp=..., arm=...) is already active. Use --force to override, or `ys end` it first." Check ys status to see what's active, and either finish it properly with ys end, or discard it and claim the slot anyway with:

bash 
ys start --exp experiments/interactive-sonnet.yaml --arm arm-sonnet --force

Bear in mind that overriding a stale run this way doesn't retroactively close out the old run's row in the database -- it was already left without an ended_at. --force only overrides the active-run slot so a new run can claim it.
