Metrics reference

Every metric below is computed per-run by ys/metrics.py, purely from the requests, tool_calls, and runs rows ys/collector.py writes while the proxy is running -- no network calls, no re-scoring, just arithmetic over already-logged data. Sections follow the source file's own grouping. Where the source itself flags a number as best-effort or approximate, that's called out here too -- read those notes before citing a number in a decision.

Tokens and cache efficiency

MetricMeaningComputed as
billable_tokens The token volume yardstick treats as cost-bearing when comparing arms. Summed over every request in the run: input_tokens + cache_creation + output_tokens + cache_read * 0.1. Cache-read tokens are weighted at 0.1 (a tenth) rather than 1.0 because they're billed at a steep discount versus fresh input tokens -- counting them at full price would make a heavily-cached arm look artificially token-expensive even though its actual dollar cost (cost_usd) is genuinely lower.
cost_usd Total billed cost of the run. Sum of each request's response_cost (as reported by the proxy).
context_high_water The largest single-request prompt size seen anywhere in the run. max() of context_tokens (input_tokens + cache_creation + cache_read) across all requests; 0 if the run has no requests.
context_growth_rate How fast prompt size trends up (or down) across the run's turns. Least-squares linear slope of context_tokens against request seq. None if the run has fewer than two requests with distinct seq values -- there's no line to fit through one point. Treat it as directional, not precise: it's a straight-line fit over however many turns the run happened to have.
cache_read_ratio What fraction of the run's total input came from cache instead of being paid for fresh. cache_read / (cache_read + input + cache_creation), summed across the run first, then divided; 0.0 if that denominator is 0 (no input tokens recorded at all).

Fixed overhead

These metrics isolate the tax a harness pays on every single turn just for repeating its system prompt and tool schemas, as opposed to tokens spent on the actual conversation.

MetricMeaningComputed as
overhead_tokens_per_turn The system-prompt + tool-schema token cost paid on a single turn. system_tokens + tools_tokens of the run's first request only -- later requests are never inspected for this number, even if they differ.
fixed_overhead_tokens Total overhead tokens spent across the whole run purely on repeating the system prompt/tools every turn. overhead_tokens_per_turn * turns -- this assumes every turn pays exactly the same fixed tax the first turn did.
overhead_share What fraction of all context tokens moved in the run was fixed overhead rather than actual conversation content. fixed_overhead_tokens / sum(context_tokens across all requests); 0.0 if that sum is 0.
overhead_drift Whether the harness actually kept its system prompt/tool schemas constant across the run. Boolean: True if any request after the first has a different system_tokens or tools_tokens count than the first request. This is the check on the assumption fixed_overhead_tokens makes above -- it flags a harness that mutates its system prompt or tool definitions mid-run, which the point-in-time overhead_tokens_per_turn number can't see on its own, since that number only ever looks at request #1.

Turns and tool calls

MetricMeaningComputed as
turns Number of model requests recorded for the run. Literally a COUNT(*) over the run's rows in the requests table.
tool_calls Total number of tool invocations logged for the run. Count of the run's rows in tool_calls.
tool_calls_per_turn Average number of tool calls issued per model turn. tool_calls / turns; 0.0 if turns is 0.
tool_error_rate Fraction of logged tool calls that came back marked as an error. n_errors / n_calls, where n_errors counts rows with is_error truthy; 0.0 if there are no tool calls at all. Caveat: the denominator is every logged tool call, not just the ones whose result was actually matched back to it. The schema can't distinguish "no result seen yet" from "resolved, no error" -- both leave is_error = 0 -- so a tool call whose matching result never arrived (a truncated log, a crash mid-call) is counted as non-error rather than excluded. This can understate the true error rate.

Redundancy

MetricMeaningComputed as
unique_tool_calls Number of distinct tool calls in the run. Count of distinct input_hash values across the run's tool calls (the hash covers the tool name and its canonicalized input).
redundant_tool_calls Number of tool calls that exactly duplicated an earlier one. total tool calls - unique_tool_calls.
redundancy_rate Fraction of tool calls that were redundant. redundant_tool_calls / tool_calls; 0.0 if there were no tool calls.
read_amplification Average number of times each distinct read/grep/glob-style call was repeated. Restricted to tool calls whose name contains "read", "grep", or "glob" (case-insensitive substring match). Those calls are grouped by (name, input_hash), and the metric is the mean group size -- total read-like calls divided by the number of distinct groups. It's None, not 0, when the run made no read-like calls at all, so "never measured" stays distinguishable from "measured as 1". Documented undercount: the schema only stores a hash of the canonicalized tool input, not the raw file path, so grouping by (name, input_hash) is a best-effort proxy for "read the same file again" -- reading the same file with slightly different arguments (e.g. a different line range or offset) hashes differently and is counted as a different "file", which undercounts true amplification.

Compaction and branching

These metrics key off transition, a per-request classification ys/collector.py assigns by comparing a request's message history against the previous request's: continuation (the history is a strict extension of what came before), compaction (the history got shorter -- the signal these metrics are built around), branch (it diverged partway through without shrinking), or reset (no shared prefix at all); a run's very first request has nothing to compare against and gets no transition.

The classifier deliberately keys off "did the history get shorter" rather than literally checking whether the first message changed, because the first message is almost always the stable system prompt -- a real mid-conversation summarization leaves it untouched and would be misclassified as a branch under the naive check.

MetricMeaningComputed as
compaction_events Number of requests in the run classified as a compaction. Count of requests with transition == "compaction".
tokens_dropped Total context size actually reclaimed by compaction events. For each compaction event (skipping the run's first request, which has no prior request to compare against): context_tokens(previous request) - context_tokens(this request), summed only when that difference is positive. A "compaction" event that didn't actually shrink context contributes 0, never a negative number.
turns_to_recompaction Average gap, in request sequence number, between consecutive compaction events. Needs at least two compaction events in the run -- with zero or one event there's no gap to measure, so it's None.
post_compaction_regrowth How fast context tokens climb back up right after a compaction. Best-effort: for each compaction event, fits a linear slope of context_tokens vs seq over up to the next 5 requests (the regrowth window) following that event, then averages the per-event slopes across the run. An event with fewer than 2 following requests contributes no slope; if none do, the result is None. The window is not truncated if it runs into a subsequent compaction event -- a real drop happening inside the window is treated as part of "what happens after compaction" rather than excluded, which can pull the slope down (or negative) when compactions happen close together.

Outcome

MetricMeaningComputed as
task_success Whether the run's success check passed. Read straight from the run's task_success column (set by ys end from the arm's success_check, or from --manual-score). True/False once the run has ended; None if the run hasn't ended yet, or its row is missing entirely.
wall_clock_s Total real time from ys start to ys end. Read directly from the run row; None until the run has ended.
active_s Total time the model itself spent generating responses. Sum of latency_ms over every request in the run, divided by 1000. Contrast with wall_clock_s: active_s only counts time inside model requests (network + inference latency per call), while wall_clock_s spans the whole run -- including whatever happens between calls: a human reading output, editing files, running tests, thinking. A run can have a large wall_clock_s and a comparatively tiny active_s if most of the wall-clock time was spent outside the model.

Which metrics get aggregated across repeats

When ys compare/ys report aggregate an arm's repeats (see the previous tutorial for the gate-filtering rules), every metric above is averaged (mean + population stdev) across the arm's gate-passing runs except two: task_success and overhead_drift are deliberately left out of that list. Per the source comment, task_success is excluded because it's the gate itself, and overhead_drift because it's a boolean finding, not a magnitude -- a mean/stdev of a true/false flag wouldn't mean anything.

Reading the caveats

A handful of these numbers are explicitly best-effort in the source, and worth keeping in mind before citing them in a decision: read_amplification undercounts when the same file is read with different arguments; tool_error_rate's denominator counts an unmatched tool call as non-error rather than excluding it; fixed_overhead_tokens assumes the first turn's overhead applies flatly to every turn (cross-check with overhead_drift); and post_compaction_regrowth's regrowth window isn't truncated at a following compaction event. context_growth_rate and post_compaction_regrowth are both least-squares slopes fit over however many data points a run happens to have -- treat them as directional trends, not precise rates.
