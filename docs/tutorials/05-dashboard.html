Using the dashboard

ys web runs a small FastAPI app that walks the same lifecycle as the CLI -- create an experiment, start a proxy, start and end runs, compare arms -- without leaving the browser. It's a thin presentation layer with no business logic of its own, so it can never drift from what the CLI does.

Starting and stopping the dashboard

bash 
ys web up             # start the dashboard (default port 8501)
ys web up --port 9000 # or on a specific port
ys web status          # is it running, and what's the pid?
ys web down            # stop it

ys web up launches uvicorn ys.web.app:app as a detached background process, waits for /health to respond, and prints the dashboard's URL. It also calls the same database initialization ys init does, so you don't need to run ys init first just to use the dashboard.

The dashboard and the measurement proxy are two completely separate processes with separate pidfiles, port files, and logs: the dashboard's are ~/.yardstick/web.pid / web.port / web.log (default port 8501), the proxy's are ~/.yardstick/proxy.pid / proxy.port / proxy.log (default port 4000). ys web down never stops the proxy, and ys proxy down never stops the dashboard -- check each independently with ys web status and ys proxy status.

The routes: same lifecycle, different transport

Every page the dashboard serves is either a plain GET (a page you read) or a form POST that redirects back to a page afterward (an action you take) -- there's no client-side routing or JSON API to speak of.

Method & path What it does
GET /Index: every experiment found in ~/.yardstick/experiments/, with its task id, arm count, and recorded run count.
GET /experiments/newThe experiment-creation form.
POST /experimentsValidates and writes a new experiment YAML, then redirects to its detail page.
GET /experiments/{name}Experiment detail: task/success-check/repeats, and every arm's recorded runs.
GET /experiments/{name}/compareRenders the same comparison as ys report --html, in the browser.
POST /experiments/{name}/proxy/upStarts the measurement proxy, scoped to just this experiment's models.
POST /proxy/downStops the proxy, then redirects back to wherever the form was submitted from.
POST /experiments/{name}/runs/startBegins a run of one arm and marks it active.
POST /runs/endEnds the currently active run (optionally with a manual score).
POST /runs/{run_id}/deleteDeletes a run and its requests/tool calls.
GET /runs/{run_id}Run detail: metrics summary, full request log, tool call log.

Creating an experiment through the form

/experiments/new accepts the same shape of data as an experiment YAML, entered as plain form fields: an experiment name (letters/digits/-/_ only -- it becomes the filename), an optional question, the fixed task (task_id, success_check, timeout_s), one or more repeatable model rows, one or more repeatable arm rows, and a repeats count.

Each model row is either mock (costs nothing, always returns the canned text you type as its response -- good for testing the pipeline) or real (routes to an anthropic/... model id using whatever ANTHROPIC_API_KEY you have exported). Each arm row picks an id, a model key that must match one of the model rows above, an optional baseline checkbox, and optional notes.

On submit, the server assembles this into the same dict shape ys.experiment.Experiment validates for the CLI -- so duplicate arm ids, more than one arm marked baseline, and other structural mistakes are rejected identically to a hand-written YAML. On success it writes ~/.yardstick/experiments/<name>.yaml and redirects to the new experiment's detail page; on a validation error it redirects back to the form with the error message in the URL.

The dashboard's experiment list only shows YAMLs that live in ~/.yardstick/experiments/. A CLI-authored experiment file living elsewhere on disk -- like this repo's experiments/example.yaml -- won't appear until you copy or recreate it there.

Experiment detail: starting and ending runs

Each arm on the experiment detail page shows a table of its recorded runs (repeat number, run id linking to its detail page, start time, success/fail/in-progress pill, wall clock time, and a delete button) plus a "start run" button. That button is hidden for every arm, on every experiment, whenever any run anywhere is currently active -- the dashboard enforces the exact same single-active-run-at-a-time rule the CLI does, because both call the same ys.runs.begin_run/finish_run functions under ys.state.

Whenever a run is active, every page in the dashboard (not just the experiment page) shows an "active run" card at the top with an inline form to end it -- including an optional manual-score field that skips success_check, exactly like ys end --manual-score. Starting a run redirects back to the experiment page with a flash message; a second start attempt while one is already active is refused with an error message rather than silently overriding the active run.

A "start proxy for this experiment" button appears on the experiment page whenever the proxy isn't already running. Unlike ys proxy up --exp, which can take several experiment YAMLs at once to serve multiple experiments' models from one proxy, this button always starts the proxy scoped to just that one experiment's models.

Compare view

/experiments/{name}/compare calls the exact same render.compare_experiment + render.render_html pipeline as ys report --html and serves the result directly as an HTML response, in the browser, instead of writing it to a file. If no arm has any recorded runs yet, it redirects back to the experiment page with the same "no runs found for any arm" error ys compare would raise on the CLI.

Run detail page

/runs/{run_id} shows the run's experiment/arm/repeat and success pill, a summary card of headline metrics (turns, billable_tokens, cost_usd, cache_read_ratio, context_high_water, tool_calls, tool_error_rate, redundant_tool_calls, compaction_events, active_s), the full per-request log (tokens in, cache create/read, tokens out, cost, transition), and the full tool-call log (name, error flag, input size). A delete button appears unless this run is the currently active one.

Deleting a run

Delete buttons on the experiment page and the run detail page both post to /runs/{run_id}/delete, which cascades the delete across that run's requests and tool calls and refuses (redirecting back with an error) if the run is currently active -- end it first. The "are you sure?" prompt on these buttons is a plain browser confirm() dialog; it's a client-side courtesy, not a server-side safeguard -- the only actual server-side protection is the active-run refusal.

What the dashboard can't do

There is no browser equivalent for pointing an agent's config at the proxy or restoring it afterward -- ys harness point / ys harness reset / ys harness status remain CLI-only.

There's no route to edit an existing experiment's YAML -- the form only creates new ones. To change an existing experiment, edit its file in ~/.yardstick/experiments/ by hand.

The compare view has no download or save-to-file option; it's rendered live on request. To get a portable, self-contained file to email or commit, use ys report --exp ... --html ... from the CLI (see the previous tutorial).
